# Этапы, агенты, отчёты и план проекта

Список задач облачного Codex не сообщает достоверный процент проекта, его полный состав агентов и будущий план. Для этих сведений Orbit принимает отдельную **сводку проекта**: JSON-файл, созданный агентом или человеком, который действительно наблюдал работу.

Сводка дополняет выбранную карточку проекта. Облачные задачи и их статусы остаются полученными из CLI; сводка не может подменить их, создать отсутствующий проект или выдать количество попыток за число агентов.

## Подключить сводку

1. Сначала получите обычный снимок из авторизованного CLI:

   ```sh
   python3 bridge/orbit_bridge.py export --output .orbit/base-snapshot.json
   ```

2. Найдите в нём `id` нужного проекта. Это устойчивый идентификатор окружения, сформированный адаптером; имя карточки не является идентификатором. Посмотреть пары имени и ID можно так:

   ```sh
   python3 -c 'import json; data=json.load(open(".orbit/base-snapshot.json")); print("\n".join(p["name"]+": "+p["id"] for p in data["projects"]))'
   ```

3. Создайте каталог `.orbit/briefs` и поместите туда сводку с этим `projectId`. Пример структуры — [examples/analytics-brief.json](examples/analytics-brief.json). **Все сведения в примере вымышлены.** Перед использованием замените идентификатор, время и содержание реальными фактами.

4. Проверьте объединение без сетевых запросов:

   ```sh
   python3 bridge/orbit_bridge.py validate-briefs --snapshot .orbit/base-snapshot.json --briefs-dir .orbit/briefs --output .orbit/combined-snapshot.json
   ```

   Полученный файл можно импортировать в Orbit на iPhone. Команда не обращается к аккаунту Codex.

5. Для последующих экспортов и сервиса добавьте каталог:

   ```sh
   python3 bridge/orbit_bridge.py export --briefs-dir .orbit/briefs --output .orbit/snapshot.json
   python3 bridge/orbit_bridge.py serve --briefs-dir .orbit/briefs --snapshot .orbit/snapshot.json
   ```

   HTTPS и отдельный токен сервиса настраиваются по [основной инструкции](README.md).

## Как сведения попадут от агента

Этот модуль **не читает внутреннее состояние агентов автоматически**. У облачного Codex и компьютера с bridge разные файловые системы. Агент может приложить сводку к результату для ручного переноса либо отправить её по HTTPS через новый клиент `publish_brief.py`. Для сетевой отправки нужно отдельно настроить сервис, HTTPS и секрет записи конкретного проекта по [PUBLISHING.md](PUBLISHING.md). Передача через репозиторий или расписание не настроена.

Пример запроса агенту, который ведёт ваш проект:

> По завершении текущего этапа создай файл `project-brief.json` для Orbit. Используй структуру из примера формата. В `projectId` укажи `<ID ИЗ СНИМКА ORBIT>`, в `producer` — понятное имя источника, в `observedAt` — реальное время наблюдения с часовым поясом. Передай только подтверждённые результаты: этап, прогресс, известный состав агентов, последние отчёты и согласованные следующие шаги. Если этап или прогресс неизвестны, передай `null` или не включай поле. Не выводи прогресс из статуса облачной задачи и не придумывай субагентов. Не меняй `AGENTS.md` или настройки других проектов. Обнови файл атомарно: сначала запиши соседний файл с окончанием `.tmp`, затем замени итоговый JSON. В ответе укажи, какой файл создан и к какому моменту относятся сведения.

Для обновления сводки на компьютере bridge используйте ту же схему: запись во временный файл **с окончанием `.tmp`**, затем атомарное переименование в итоговый `.json`. Bridge игнорирует скрытые файлы и файлы без окончания `.json`, поэтому не прочитает частично записанный временный документ.

## Поля и смысл времени

Обязательные поля:

| Поле | Значение |
| --- | --- |
| `projectId` | Точное значение `id` существующего проекта из снимка Orbit, до 120 символов |
| `observedAt` | Когда источник наблюдал сведения; ISO 8601 с часовым поясом |
| `producer` | Имя источника, 1–80 символов |

Нужно передать хотя бы одно поле сведений: `name`, `subtitle`, `symbol`, `stage`, `progress`, `agents`, `reports` или `steps`.

- `stage`: `discovery`, `development`, `testing`, `delivery` или `null`.
- `progress`: число от 0 до 1 или `null`. Это явное значение источника; адаптер его не рассчитывает.
- `agents`: до 12 записей с `id`, `name`, `role`, `status`, `currentTask`. Статусы: `working`, `waiting`, `completed`.
- `reports`: до 50 записей с `id`, `title`, `summary`, `createdAt`, `highlights`.
- `steps`: до 50 записей с `id`, `title`, `detail`, `isComplete`; последнее поле — JSON `true`/`false`.
- `name`, `subtitle`, `symbol`: необязательные подписи карточки. Поле `symbol` — имя SF Symbol, поддерживаемого iPhone.

**Отсутствующее поле сохраняет исходные сведения; явно переданный пустой список заменяет соответствующий список пустым.** Поэтому файл, содержащий только новые `reports`, не удалит уже переданные `agents`. Однако при обычном опросе исходный снимок заново создаётся из CLI: для постоянного показа агентов их нужно сохранять в сводке, а не рассчитывать на прежний результат объединения.

Время сводки сохраняется отдельно в `briefUpdatedAt`, источник — в `briefSource`. Новое получение списка задач не делает старую сводку новой. `updatedAt` проекта — более позднее из известного времени задач и времени сводки; это поле не заменяет отдельное время сведений об агентах. Часовой пояс нормализуется к UTC. Разрешена погрешность часов до пяти минут; более далёкое будущее отклоняется. Время отчёта не может быть позднее времени наблюдения более чем на пять минут.

## Ошибки и ограничения

В каталоге допускается до 12 видимых JSON-файлов, по одному на проект, каждый до 256 КиБ. Файлы должны быть обычными: символьные ссылки и другие типы файлов отклоняются. Итоговый снимок ограничен 2 МБ. Идентификаторы записей непустые, до 120 символов, уникальны внутри своего списка.

Ограничения строк: имя проекта/агента и `producer` — до 80 символов; `subtitle` — до 300; `symbol` — до 80; роль агента — до 160; задача агента и описание шага — до 4000; заголовки отчёта/шага — до 300; сводка отчёта — до 20000; до 50 пунктов `highlights`, каждый до 2000 символов. Неизвестные поля и повторные JSON-ключи отклоняются, чтобы опечатка не исчезла незаметно.

Несуществующий каталог, неправильный `projectId`, две сводки одного проекта или некорректный документ останавливают обновление целиком. При работе сервиса остаётся предыдущий успешный снимок с признаком устаревших данных; частичное объединение не публикуется. Если окружение удалено или больше не входит в выбранный `--env`, удалите или переназначьте его сводку: привязка по имени или создание вымышленных проектов не выполняется.

Тесты используют только синтетические документы:

```sh
python3 -m unittest discover -s bridge -p test_project_briefs.py -v
```
